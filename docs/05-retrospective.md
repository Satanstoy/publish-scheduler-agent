# 05 复盘

## 1. 实际用时

本次会话从读题到最终代码审查约 **70 分钟**（2026-11-10 20:03–21:15，按本机 shell 时间），不含候选人阅读、复核、补 key 和 GitHub 发布。题目建议投入 3 小时，本次低于建议时长；剩余时间应该用于：

- 候选人逐行复核代码和文档。
- 用真实 OpenAI-compatible key 重跑 live 模式。
- 检查 GitHub 仓库公开性和最终 commit SHA。
- 补跨天、批量压力和真实文件系统失败测试。

## 2. 最难的问题

### 2.1 硬约束和软约束的草稿边界

最容易犯的错是把“建议 19:00”直接保存成硬约束的替代草稿。题目的参考实例又说“模型建议 19:00 并标记待确认”，容易让人以为所有冲突都可以落草稿。

最后的处理是：

- `hard` 冲突不落草稿，只给备选，`blocked_conflict`。
- `preferred` 冲突落替代草稿，`pending_user_confirmation`。
- 工具层 `save_draft` 强制检查，不依赖模型自觉。

这个取舍牺牲了“硬约束也能先生成草稿”的便利，换取不会擅自改变硬性要求。

### 2.2 重复提交与自冲突

第一次实现时，重复运行很容易出现：第一次生成 19:00 草稿，第二次查询时 19:00 被自己的草稿占用，Agent 改存 20:00，产生第二份草稿。

解决方式是把判重指纹放进查询：

- 指纹 = `material_id + content_version + 日期 + 时间 + 约束 + 渠道`。
- `query_slots` 排除同指纹草稿。
- `save_draft` 在锁内再查一次指纹。
- 草稿 ID 由指纹确定性生成。

测试用 8 个线程同时保存同一请求，确认只产生一份草稿。

### 2.3 保存失败不能虚报

模型很容易在 `save_draft` 返回错误后继续用“已保存”措辞结束。解决方式不是加一句提示，而是改结构：

- 模型不写最终报告。
- 工具把结果写进 ledger。
- `report.build` 从 ledger 生成 `draft.save_status`、`error`、`outcome`。
- 保存失败时 `draft.id=null`，`outcome=needs_attention`，CLI 退出码 1。

live Trace 里模型先写错参数、被工具拒绝、修正后仍保存失败，最后如实报告；这条路径比单纯的成功路径更能说明护栏有用。

### 2.4 没有可用直连 key 时怎么做真实 Trace

本机 `opencode-go` 直连 key 返回 `api_key_expired`。如果只交离线 mock，文档必须承认“没验证真实模型决策”，评分会弱。

最后用了本机 OpenCode 服务的实验性 `generate/text`，走文本 JSON 协议，产出 6 条真实模型 Trace。这不是标准 OpenAI-compatible 路径，所以文档明确标注：

- live Trace 是本机实验接口的真实模型行为。
- 标准 live 模式保留，评审可自备 key。
- 离线 mock 仍然可复现全部验收。

### 2.5 上限和批量规模的矛盾

默认 12 步 / 20 次调用，对单素材验收足够；5 个素材各走 4 个工具再加 finish 会超过 20 次。当前选择是保留默认上限，CLI 允许调高，并在文档里说明批量五条可能触发 `incomplete`。

如果重新设计，我会把上限按“每素材预算 + 全局预算”组合，而不是一个固定全局数字。

## 3. 做得好的地方

- 先写测试再写实现，红灯和绿灯都有 commit 记录。
- 工具层强制前置条件、硬约束和幂等，模型不能绕过。
- 报告由 ledger 生成，模型不能虚报保存状态。
- 真实模型 Trace 展示了三种调整：提前 finish 被拒、参数错误修正、保存失败如实结束。
- 离线 mock 和 live 共用同一套工具/报告/Trace，没有两套分叉逻辑。

## 4. 如果重做

1. 先定义 `outcome` 和 `status` 的区别，再写报告；这次是测试暴露后才补。
2. 把 `confirm` 的冲突错误也做成结构化 JSON，而不是依赖 CLI 的 store error。
3. 用 SQLite 替代 JSON + 文件锁，跨进程和压力测试会更容易。
4. 增加跨天替代和草稿 supersede，业务上更完整。
5. 给 live 模式加一个 fake OpenAI server 集成测试，减少对真实 key 的依赖。
6. 在 spec 阶段就写清楚“批量 5 条是否需要更高默认上限”。

## 5. 面试可能被问到的点

- **为什么不用 LangGraph/ADK？** 核心链路小，手写循环更容易展示工具调用、观察、调整和上限控制；框架不额外加分。
- **为什么不让模型直接输出最终 JSON？** 模型会虚报保存成功；报告必须由 ledger 生成。
- **硬冲突为什么不能保存备选草稿？** 草稿也是排期 artifact，保存替代时段等于改变了硬性要求；只能建议，等用户改请求。
- **重复提交怎么防？** 指纹不含 `request_id`，查询排除同指纹草稿，保存在锁内二次检查，ID 由指纹确定。
- **保存失败怎么测？** `--fault save_draft` 注入；单元测试和 CLI 测试都断言 store 无草稿、输出 `SAVE_FAILED`。
- **怎么证明 ReAct？** live Trace 的 `next_action` 链：finish 被拒后转 check_rules；save 参数错误后重试；硬冲突查询后不保存。
- **mock 和 live 的边界？** mock 证明流程和护栏；live 证明当前模型在当前环境的行为，不证明稳定性。
