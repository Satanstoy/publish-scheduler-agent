# 00 Grill 记录

- 题目：素材审核与发布排期 Agent（题 1）
- 记录时间：2026-11-10
- 目标：在 3 小时左右做出可运行、可测试、可审计的 CLI Agent，优先核心链路，不追求 UI 与线上部署。

## 项目画像

一个内容排期操作员把“待审素材 + 发布时间要求”交给 CLI。Agent 依次读取素材、检查规则、查询时段、保存草稿，最后输出每项素材的审核状态、风险原因、建议时段、待确认项和草稿保存状态。系统只写草稿，不接真实发布。

技术形态定为 Python 3.12 + CLI + JSON 文件 + pytest。模型负责选工具和调整下一步，确定性控制器负责工具白名单、执行上限、硬约束、幂等和结果对账。模型可以建议，不能绕过护栏。

## 七个决策

| # | 问题 | 结论 | 主要理由 |
| --- | --- | --- | --- |
| 1 | 硬约束冲突时草稿怎么落 | 硬冲突不落草稿，返回 `blocked_conflict` 和备选时段；软冲突才写替代时段草稿并标 pending | 避免被判定“擅自改变硬性发布要求” |
| 2 | 真实模型 Trace 怎么产出 | 优先用本机 OpenCode 凭证；同时保留离线 mock 和标准 OpenAI-compatible live 模式 | 本地直连 key 已过期，但本机 OpenCode 服务的 `generate/text` 可用 |
| 3 | 重复提交判重指纹 | `material_id + content_version + 要求日期/时间 + 约束类型`；`request_id` 不参与 | 同一请求重复保存只产生一份草稿；内容更新后可产生新草稿 |
| 4 | “可确认”做到哪一步 | 两阶段 CLI：`run` 产出草稿与待确认项，`confirm` 只把草稿标为已确认，仍然不发布 | 用代码证明确认边界，而不是只在报告里写一句话 |
| 5 | 批量规模与执行上限 | 一次最多 5 个素材；默认全局 12 个模型步、20 次工具调用；到上限逐项返回 `incomplete` | 满足题目对步数/调用次数上限的要求，并保留部分结果 |
| 6 | 规则风险如何处理 | 硬规则违规阻断；软警告可落草稿但必须 pending | 版权、禁词、黑名单日期不能带风险排期；临期和长视频需要人工判断 |
| 7 | GitHub 仓库 | 先本地 git，开发完成后登录 `gh` 或提供仓库地址再 push | 不阻塞开发；最终提交仍需 GitHub URL 和 commit SHA |

## 不可协商约束

1. 工具注册表里没有 `publish` 工具，任何输出都固定 `published=false`。
2. 硬约束冲突时，`save_draft` 必须拒绝替代时段；模型只能报告备选，不能写草稿。
3. 保存结果以 store ledger 为准。模型说“已保存”但 ledger 没有草稿时，报告必须显示失败。
4. 相同请求指纹重复保存只能产生一份草稿；重复运行返回原草稿并标 `existing`。
5. 保存失败必须返回 `save_failed`，不得用“稍后重试”“已提交”等话术掩盖。
6. 达到步数或工具调用上限时，未完成素材必须返回 `incomplete`，不能伪造终态。

## 关键假设

- 时区固定为 `Asia/Shanghai`，请求日期和时间为本地时间。
- 排期冲突按同一 `channel` 判断；当前示例全部使用 `wechat`。
- 替代时段只在同一天的工作时段（09:00–22:00）内搜索，步长 30 分钟。
- 已保存草稿会占用规划时段；同一请求指纹的草稿在查询时排除，避免重复运行把自己判成冲突。
- `submitted_at` 作为规则检查的“当前时间”，用于临期判断；示例固定为 `2026-11-10T09:00:00+08:00`。
- 素材的 `content_version` 变化视为新内容，允许生成新草稿；旧草稿不自动覆盖或取消。

## 遗留风险

- 本机 OpenCode 的直连 API key 返回 `api_key_expired`。live Trace 计划走本机 OpenCode 服务的 `POST /api/experimental/generate/text`，该接口是实验性接口，评审环境不一定可用；因此标准 OpenAI-compatible 模式和离线 mock 都必须可用。
- JSON 文件存储只保证单机进程内和单机多进程的顺序一致性，不做跨机器并发。
- 不实现草稿取消、替换、历史版本对比；内容更新后的旧草稿需要人工处理。
- 不接真实发布系统，不实现账号、权限和审计日志。
